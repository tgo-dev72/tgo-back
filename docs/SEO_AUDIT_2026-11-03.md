# TijaraGO SEO foundation audit

Date: 2026-11-03
Scope: public TijaraGO showroom and merchant storefronts
Repositories: `store-platform` and `design-stock`

## Executive summary

TijaraGO has a useful client-side storefront metadata utility, crawlable anchor links, product SEO fields, localized storefront copy, semantic breadcrumbs, responsive image helpers, and a verified primary-domain model. These are good foundations, but the production delivery layer is not yet search-engine safe.

The showroom and generated storefronts are Vite single-page applications. A direct crawler request receives only the shared build-time `index.html`; page-specific metadata and JSON-LD are added after JavaScript and API requests complete. Production `robots.txt` and `sitemap.xml` currently return that same HTML document with HTTP 200. Dashboard, platform-admin, authentication, preview and demo surfaces are not protected by a valid robots response or an initial `noindex` directive.

The highest priorities are therefore:

1. provide real environment-aware robots responses and block private/preview applications;
2. provide real XML sitemaps containing only canonical public routes;
3. make essential metadata available in initial HTML rather than only after hydration;
4. establish a single server-authoritative canonical origin per merchant;
5. add tenant-aware storefront SEO configuration, redirects and sitemap generation.

## Architecture discovered

- Backend: Django/DRF on `api.tijarago.com`.
- Public showroom: React + Vite SPA in `design-stock/apps/showroom`.
- Dashboard and platform-admin: separate React + Vite SPAs.
- Merchant storefronts: generated Vite apps sharing `packages/storefront-core`.
- Routing: React Router for the showroom; History API routing inside storefront-core.
- Hosting: Vercel static applications with catch-all rewrites to `/`.
- Merchant tenancy: API requests carry `X-Store-Slug`; verified custom domains are bound to one store.
- Canonical merchant hostname data: `StoreConfig.domain` plus verified `StorefrontDomain` rows.
- Rendering: no SSR or build-time prerendering for dynamic merchant pages.

## Findings

### SEO-001 — robots and sitemap paths return HTML

- Severity: critical
- Scope: public website and merchant storefronts
- Locations: `apps/*/vercel.json`, generated storefront `vercel.json`
- Routes: `/robots.txt`, `/sitemap.xml`
- Current behavior: catch-all rewrites serve `index.html` with HTTP 200.
- Impact: crawlers receive no reliable indexing policy or discovery document; HTML is mislabeled by path as robots/XML.
- Recommendation: ship real static policies for fixed applications and tenant-aware responses for merchant hosts. Preview/demo/private applications must disallow crawling.
- Verification: assert status, content type and body grammar in unit and production smoke tests.

### SEO-002 — private applications and routes are indexable by default

- Severity: critical
- Scope: showroom private routes, dashboard, platform-admin, storefront account/checkout, previews
- Locations: showroom and private-app `index.html`/Vercel configuration; `storefront-core/src/storefront/seo.ts`
- Current behavior: dashboard/admin initial HTML has no `noindex`; showroom login/signup/private routes inherit public metadata; account adds `noindex` only after JavaScript.
- Impact: private or low-value URLs may enter search indexes and expose misleading snippets.
- Recommendation: initial `noindex, nofollow` for private applications, route-specific initial policy for showroom auth/private routes, and `X-Robots-Tag` on preview/staging responses.
- Verification: crawler-style HTML/header tests without JavaScript.

### SEO-003 — essential metadata depends on client execution

- Severity: high
- Scope: showroom and merchant storefronts
- Locations: `apps/showroom/index.html`, `packages/storefront-core/src/storefront/seo.ts`
- Current behavior: showroom routes share one title/description; storefront title, description, canonical, OG, Twitter and JSON-LD are injected in a React effect.
- Impact: non-rendering crawlers and link unfurlers see generic or missing metadata. Dynamic product data is invisible in initial HTML.
- Recommendation: prerender fixed showroom routes and introduce a server/edge-rendered SEO shell for merchant canonical routes. Retain client updates for navigation, but do not rely on them as the only source.
- Verification: direct HTTP HTML must contain expected metadata before JavaScript.

### SEO-004 — canonical origin is client-derived and not authoritative enough

- Severity: high
- Scope: merchant storefronts
- Location: `packages/storefront-core/src/storefront/seo.ts`
- Current behavior: canonical origin uses `config.domain`, falling back to `window.location.origin`.
- Impact: deployment, preview, alternate subdomain and custom-domain variants can self-canonicalize, creating duplicate indexing.
- Recommendation: API must return one verified `canonicalOrigin` and an explicit `indexingAllowed` flag. Noncanonical hosts should redirect permanently when safe or emit `noindex` plus canonical.
- Verification: default/custom/provider/preview hostname matrix tests.

### SEO-005 — no sitemap generation or tenant isolation

- Severity: high
- Scope: both
- Locations: no implementation found
- Current behavior: no valid sitemap exists.
- Impact: weak route discovery and no guarantee that only active, public tenant resources are exposed.
- Recommendation: static showroom sitemap; tenant-specific merchant sitemap containing only the canonical homepage, visible CMS pages, visible categories and active products. Escape XML and cache by tenant/publication revision.
- Verification: XML schema/content-type tests, tenant isolation tests and inactive-resource exclusions.

### SEO-006 — merchant SEO data contract is incomplete

- Severity: high
- Scope: merchant storefronts
- Locations: `StoreConfig`, `CatalogSection`, `Product`
- Current behavior: products have `seo_title` and `seo_description`; store and category SEO overrides, social image, indexing preference and title template are absent.
- Impact: merchants cannot control key snippets consistently and categories reuse a generic store description.
- Recommendation: backward-compatible validated fields with safe fallbacks. Keep tenant ownership checks and add non-destructive length warnings.
- Verification: model/serializer/API tests for overrides, fallbacks, Unicode and injection-like input.

### SEO-007 — slug changes have no permanent redirect history

- Severity: high
- Scope: merchant products and categories
- Locations: product/category models and merchant serializers
- Current behavior: slugs can change, but no old-path mapping or redirect route exists.
- Impact: backlinks and indexed URLs become soft 404s and lose accumulated signals.
- Recommendation: tenant-scoped redirect history with loop prevention and permanent redirects only within the same canonical store.
- Verification: slug-change, collision, loop and cross-tenant tests.

### SEO-008 — unknown SPA routes redirect client-side to the homepage

- Severity: medium
- Scope: showroom and storefronts
- Locations: showroom catch-all `<Navigate>` and Vercel catch-all rewrite; storefront product-missing UI
- Current behavior: server returns 200 SPA shell; showroom then navigates home. Missing products render a client-side unavailable state.
- Impact: soft 404s and duplicate URLs.
- Recommendation: real 404 response for unknown public routes and a useful crawlable 404 document.
- Verification: direct HTTP status and rendered content tests.

### SEO-009 — multilingual UI has no URL-level language architecture

- Severity: medium
- Scope: both
- Current behavior: locale changes client-side and `<html lang>` is updated after loading; there are no locale-specific canonical URLs or reciprocal hreflang links.
- Impact: English/French/Arabic variants cannot be indexed as distinct localized pages reliably.
- Recommendation: choose a locale URL strategy (`/fr/`, `/ar/`, `/en/`) before implementing hreflang. Do not emit hreflang until reciprocal URLs genuinely exist.
- Verification: reciprocal hreflang and `x-default` tests after the routing decision.

### SEO-010 — structured data is useful but incomplete and client-only

- Severity: medium
- Scope: merchant storefronts
- Location: `packages/storefront-core/src/storefront/seo.ts`
- Current behavior: OnlineStore, CollectionPage and Product JSON-LD exist; product rating is emitted only when reviews exist. No seller/brand/breadcrumb structured data is emitted. It is inserted after hydration.
- Impact: limited eligibility and unreliable crawler/unfurler visibility.
- Recommendation: render server-side; add BreadcrumbList and verified seller/brand fields. Continue omitting unavailable or fabricated claims.
- Verification: JSON serialization and schema-shape tests using real catalog values.

### SEO-011 — search/filter query duplication is not controlled

- Severity: medium
- Scope: merchant storefronts
- Locations: collection/search navigation in storefront-core
- Current behavior: `?search=` and sorting/filter state can produce many crawlable URL variants while canonical metadata ignores most query state only after hydration.
- Impact: crawl-space expansion and duplicate content.
- Recommendation: initial canonical to the clean collection URL and `noindex,follow` for internal search/filter combinations; never include them in sitemaps.
- Verification: query matrix tests.

### SEO-012 — good image foundations, uneven dimensions

- Severity: low
- Scope: both
- Current behavior: important showroom screenshots declare dimensions and lazy loading; storefront uses an optimized image component. Some gallery and merchant-derived images lack explicit dimensions or descriptive text.
- Impact: possible CLS and weaker image accessibility/discovery.
- Recommendation: preserve intrinsic dimensions/aspect ratio through API data and require useful merchant alt text with safe fallbacks.
- Verification: browser layout and accessibility checks.

## What is already working

- Product SEO title and description fields are tenant-scoped.
- Product slugs are unique per store.
- Public product queries include only active products.
- Public categories use visibility flags.
- Verified custom-domain records are tenant-bound.
- Storefront navigation uses real anchor URLs for products, categories and pages.
- Semantic breadcrumb navigation is present visually.
- JSON-LD uses `JSON.stringify` through `textContent`, avoiding HTML interpretation.
- Product offers use actual price, currency and inventory state.
- Aggregate ratings are omitted when there are no reviews.
- Arabic `lang`/`dir` handling and reduced-motion support exist client-side.
- Responsive image helpers and several explicit width/height attributes are present.

## Phase 2 implementation — merchant SEO and initial HTML

Status: implemented and verified locally on 2026-11-04; not deployed.

### Selected rendering architecture

The showroom now uses build-time prerendering because its approved public routes are finite and their content ships with the application. The build creates route-specific `index.html` documents for `/`, `/pricing`, `/gallery`, `/how-it-works`, `/terms`, and `/privacy`.

Generated merchant storefronts keep the existing Vite/React architecture. A generated Vercel server function reads the built SPA shell, requests tenant-owned metadata from the Django API, and injects title, description, canonical, robots, Open Graph, Twitter and JSON-LD before returning the first HTML response. This avoids a framework migration and keeps catalog/publication decisions in the trusted backend. The response is `private, no-store`, so one tenant's rendered metadata cannot be served from a shared HTML cache. Client-side metadata remains supplementary for in-app navigation.

### Database migrations

- `store/0028`: adds `Store.is_suspended` and store SEO title, description, social image and indexing opt-in fields. Existing stores default to indexing disabled.
- `catalog/0016`: adds collection SEO title, description and social image plus product social image.
- `catalog/0017`: adds tenant-scoped product and collection slug history with uniqueness constraints and cascading cleanup.

### Public endpoints and delivery configuration

- `GET /api/public/storefront/<slug>/robots.txt`
- `GET /api/public/storefront/<slug>/sitemap.xml`
- `GET /api/public/storefront/<slug>/seo?path=<public-path>`
- Public storefront configuration now supplies `canonicalOrigin`, `indexingAllowed`, and store SEO fallbacks.
- Generated Vercel projects rewrite robots and sitemap paths to Django and public page requests to `api/seo-render.mjs`; account paths also receive `X-Robots-Tag` protection.

### Canonical-origin rules

1. Use an IDNA-normalized HTTPS custom hostname only when it is tenant-owned, primary, active, provider-verified, certificate-valid, and health-verified.
2. Otherwise use `https://<store-slug>.<STOREFRONT_BASE_DOMAIN>`.
3. Never read `Host`, `Origin`, `Referer`, `X-Forwarded-Host`, Vercel URLs, preview URLs, localhost, a path, query string, or fragment.
4. During domain switching, the old healthy primary remains canonical until the replacement completes verification and is made primary.
5. Pending/disabled custom domains never become canonical. Preview/demo visits cannot change canonical output.

### Effective indexing decision

All checks are conjunctive and fail closed.

| Check | Required to index | Failure result |
| --- | --- | --- |
| Environment | production flag enabled and Django debug off | noindex: `environment_disabled` |
| Merchant preference | `allow_search_indexing=true` | noindex: `merchant_opt_out` |
| Suspension | store not suspended | noindex: `store_suspended` |
| Preview state | not a theme demo store | noindex: `preview_store` |
| Publication | latest request is live, created and deployed | noindex: `store_unpublished` |
| Canonical domain | primary domain active, verified, valid TLS and healthy | noindex: `domain_not_ready` |
| Ownership | active owner exists | noindex: `owner_inactive` |

Non-indexable metadata responses include initial robots metadata and `X-Robots-Tag`; robots disallows all and sitemap returns 404. Authentication remains the protection for private data.

### Sitemap, cache and invalidation behavior

Tenant sitemaps contain only the canonical homepage, active products, visible collections and visible published content pages. URLs are absolute, deterministically sorted, deduplicated and XML-escaped. Product/page `lastmod` is emitted only from persisted update timestamps. Account, authentication, cart, checkout, search/filter queries, previews and inactive resources are excluded.

SEO, robots and sitemap responses currently use `private, no-store`. This deliberately trades cache performance for immediate correctness after publication, deletion, slug, domain or indexing changes and eliminates cross-tenant cache leakage/invalidation risk. Before catalogs approach the 50,000 URL sitemap protocol limit, add tenant-scoped sitemap indexes/partitions; current product limits do not require this yet.

### Structured data and merchant data

Initial storefront HTML emits real `OnlineStore`, `WebSite`, `Product`, `Offer`, `CollectionPage`, and `BreadcrumbList` data where applicable. Product offers use persisted price, currency and calculated inventory; seller and optional real vendor/SKU/image data are included. No ratings or claims are fabricated. JSON is serialized with `<` escaped, and HTML attributes/text are encoded. Existing product image `alt_text` support is retained.

Store, product and collection SEO overrides accept French and Arabic Unicode, reject HTML markup, preserve content within explicit model lengths, and fall back to real store/resource data. Dashboard storefront settings expose store title, description, social image and the explicitly gated indexing opt-in with character guidance; product editing exposes the social image override.

### Slug history and redirects

Changing a product or collection slug records the previous tenant-scoped slug. Every historical slug resolves with HTTP 308 directly to the latest canonical path, preventing chains. Historical reuse/collisions are rejected within the tenant/resource namespace. Redirect records cascade when the target resource is deleted, so deleted/private resources cannot redirect to unrelated content. Redirect destinations are constructed only from the authoritative origin and persisted current slug.

### Remaining production actions, risk and rollback

Do not deploy until all of the following are completed:

1. Apply migrations before deploying code, but keep `STOREFRONT_INDEXING_ENABLED=false` initially.
2. Deploy API and regenerated storefront delivery logic, verify representative unpublished and opted-in tenants, then enable the production indexing flag only after domain health checks pass.
3. Regenerate/redeploy existing merchant storefronts so they receive the server renderer and rewrites.
4. Submit verified canonical sitemaps in Search Console only after raw production checks pass.

Post-deployment checklist:

```bash
curl -i -A Googlebot https://STORE.example/robots.txt
curl -i -A Googlebot https://STORE.example/sitemap.xml
curl -i -A Googlebot https://STORE.example/products/PRODUCT-SLUG
curl -i -A Googlebot https://STORE.example/collections/COLLECTION-SLUG
curl -i -A Googlebot https://STORE.example/account
curl -i -A Googlebot https://VERCEL-DEPLOYMENT.example/products/PRODUCT-SLUG
```

Confirm HTTP status/content type, authoritative canonical, raw metadata/parseable JSON-LD, account/preview noindex, and that every sitemap URL returns 200 without an avoidable redirect.

Primary operational risk is a malformed generated rewrite/function or enabling indexing before canonical domain health is established. Roll back by setting `STOREFRONT_INDEXING_ENABLED=false` (immediate fail-closed noindex), restoring the previous storefront generator/deployment, and reverting application code. The additive nullable/defaulted schema can remain safely during code rollback; remove fields/history tables only in a later reviewed migration after confirming no data is needed.
